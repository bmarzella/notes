# Dynamic Branch Prediction
## The Branch History Table
To predict branch outcome on the fly, we need a **history table**.

>**Branch History Table (BHT):** *Stores the outcome of each branching decision as a `0` (not taken) or `1` (taken). Indexed by the lower portion of the address of the branch instruction.*

The number of bits for each instruction depends on how we are predicting the next decision.

| **Branch Instruction Address (Index)** | Decision Bit(s)                               |
| -------------------------------------- | --------------------------------------------- |
| `0x00400004`                           | `01` - Branch not taken, then branch taken    |
| `0x00400008`                           | `00` - Branch not taken, then not taken again |
| etc...                                 | etc...                                        |
## Simple Predictors
### One-Bit Predictors

> *Predicts the next decision will match the previous one. Best for long, repetitive loops (where the decision stays the same). Fumbles on a single mistake and takes 2 mispredicts to recover on loops.*
#### How does it work?
One-bit predictors do exactly what they say on the tin. The `BHT` stores a single taken/not taken bit, and we predict that the branch decision will match the previous. If we previously branched, then branch again. If not, then don't.
#### When does it work?
This is useful in situations where we're likely to repeat the same decision. For example, `for(1,10000)`. The history (generally, remember we're not storing the whole history, in this case just the final bit) will look like `11111111`, and will continue to do so for the next 9998 decisions or so, so we can pretty safely predict that we'll branch the next time we have to decide.
#### When doesn't it work?
It flips its prediction immediately on a single mispredict. It's reasonable to guess `1` after `111111111111111111111111111111111111110`, but one-bit would start guessing `0`.

**During a given loop, it'll mispredict twice:**
1. At the very start, given the loop has ran before, because the table will look at the previous time that loop occurred, see that at the end of the loop we didn't branch, and guess that we don't branch, which, given we are starting the loop, is the wrong decision.
2. At the very end, because the loop is meant to terminate instead of continuing to loop.
### Two-Bit Predictors

>*Predicts using a 2-bit counter with inertia. Requires two consecutive mistakes to flip its overall prediction preventing single outliers from ruining future accuracy.*
#### How does it work?
Two-bit predictors store the previous two decisions and use a finite state automata to decide on whether to branch or not. There are four states:

|**Bit Value**|**State Name**|**Action (Prediction)**|
|---|---|---|
|`11`|**Strongly Predict Taken**|Predict **Taken**|
|`10`|**Weakly Predict Taken**|Predict **Taken**|
|`01`|**Weakly Predict Not-Taken**|Predict **Not-Taken**|
|`00`|**Strongly Predict Not-Taken**|Predict **Not-Taken**|

*Basically, if we're top right or bottom left, we're confident an upcoming decision will be what we've seen twice in a row. If we're wrong, we still think that it'll be the same, but if we're wrong again, we're confident that the pattern has flipped.*

#### When does it work?
This is excellent for repeated loops. When a loop finishes, the single not-taken outcome drops the state from `11` to `10`, meaning if the loop runs again later, it'll predict to take the branch right away. This reduces loop mispredictions from 2 down to 1 per loop, only mispredicting when the loop terminates.

Also ideal for branches that usually go one way, such as error checks (most of the time the code will function as intended, we don't want a single error to cause the code to assume that we'll always have an error).
#### When doesn't it work?
1. Branches that swich directions every 1-2 cycles, for example `1, 1, 0, 0, 1, 1, 0, 0, ... `
2. Branches whose outcome depends on random input data, for example `if (random_bit == 1)`.

## The Branch Target Buffer

> **The Branch Target Buffer (BTB)**: *A small, ultra-fast cache in the `IF` stage. Stores the target destination address of recently taken branches.*
### Why do we need it?
The BHT only helps us decide whether we should jump or not, but at the `IF` stage, the ALU hasn't calculated `PC + Offset` yet!
Without the BTB, even if the BHT tells us to predict a branch, the **CPU wouldn't know where to jump until the `EX` stage, forcing a stall.** 
**The BTB solves this by caching the target address from the last time that branch ran, allowing the CPU to jump instantly in cycle 1.**
### How does it work with the BHT?
When an instruction is fetched at address held by the `PC`, we:
1. Check BHT & BTB at the same time:
	- BHT tell us whether to predict taking the branch or not.
	- BTB checks whether it has the address (hit) or it doesn't (miss).
2. Decide the next `PC` address:
	1. BTB Hit + Predict Taken: Next `PC` address is the saved target address.
		- We have the address we'd branch to and we think that we'll have to branch.
	2. BTB Hit + Predict Not Taken: Next `PC` = `PC + 4`.
		- We don't think we'll branch so load the address of the next instruction.
	3. BTB Miss: Next `PC` = `PC + 4`.
		- Regardless of whether we think we'll branch or not, it doesn't really matter if we don't know where to branch too!
		- So, the safe bet is just to assume the next instruction is the next instruction sequentially.
### What does the BTB look like?
| **Branch PC (Index)** | **Target Address (Target PC)** |
| --------------------- | ------------------------------ |
| `0x00400004`          | `0x00400080`                   |
| `0x0040001C`          | `0x00400200`                   |
| etc...                | etc...                         |
