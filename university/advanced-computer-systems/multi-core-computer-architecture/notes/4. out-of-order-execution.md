# What is Out-of-Order Execution
Traditionally, we think of instructions running in a strict queue. If instruction 1 is stuck waiting for memory, instructions 2 and 3 must wait behind it, even if they are independent and ready to run. 

> **Out-of-Order Execution lets the CPU skip stalled instructions and run later, independent instructions such that the hardware can be kept busy.**

# How does Out-of-Order Execution Work?
To allow instructions to bypass each other when operands (inputs) aren't ready, the `ID` decode stage of our MIPS pipeline is split into two sub-stages:
1. **Issue:** Decode instructions *in program order* and check for [[2. processor-and-pipeline-fundamentals#Processor and Pipeline Fundamentals#Pipeline Hazards|structural hazards]], in this case, whether there's a *reservation station* (a buffer) available to hold it. 
	- If there is a free buffer, the instruction is issued out of the fetch buffer into the reservation station.
2. **Read Operands:** Hold the instruction in the reservation station until there are no [[2. processor-and-pipeline-fundamentals#Processor and Pipeline Fundamentals#Data Hazards|data hazards]] (input data is ready), then grab the values and execute. 
	- Once ready, we read the inputs and send the instruction to the execution unit out of order.

> *Essentially, instead of every instruction having to wait behind stalling instruction 1, instruction 1 is moved out of the way into a buffer and waits there, and the other instructions can continue executing.*
## Issues with Out-of-Order Execution
Normally, if we are executing instructions in order, then, say, if instruction 2 crashes, every instructions beforehand has been completed and nothing afterwards has touched the CPU state.
However, in OoO, this isn't necessarily the case:
- **Later instructions may already be finished:** Instruction 3 wrote its result to a register before instruction 2 crashed.
- **Earlier instructions might still be running:** Instruction 1 didn't finish before instruction 2 crashed.
We can also see **false data dependencies:**
- **WAR (Write-After-Read):** A later instruction finishes fast and overwrites a register before an earlier instruction gets to read its old value.
- **WAW (Write-After-Write):** A later instruction finishes first and writes to a register, only for an earlier, slower instruction to overwrite it later with stale data.

This causes a big issue for us. We cannot safely handle the crash or save state because our CPU state is a mess. Fixing this requires some mechanism that makes the execution *look* in order from an outside perspective.
